# Аудит геолокации нод — 10 сентября 2026

Нашёл способ улучшить обнаружение и разбор ошибок бесплатно. Не нашёл
бесплатную базу, которую можно просто поставить вместо текущей и обоснованно
считать более точной для всех нод. Проверка выявила два сильных примера неверной
городской привязки, включая исходный адрес; остальные расхождения требуют проверки.

Работа выполнена в `experiment/node-geolocation-audit`. Production использован
только для чтения настроек, кэша геолокации нод и опубликованных файлов карты.
Изменений production, исправлений точек вручную и изменений runtime-кода нет.

## Почему существующая проверка пропускает ошибки

1. `src/geoip.rs` получает город и координаты от ip-api.
2. `src/node_locations/ipinfo.rs` запрашивает **IPinfo Lite**. В структуре ответа
   отсутствуют город, регион и координаты. Это соответствует
   [официальному составу бесплатного API](https://ipinfo.io/developers/ipinfo-api).
3. `CachedGeoLocation::ipinfo_conflict_reason()` в `geo_cache.rs` сравнивает
   только страну. При одинаковом `AU` Nyngan не может вызвать конфликт с Sydney.
4. `tiebreak::resolve_conflicts()` вызывается для конфликтов стран. Когда
   ipwho.is совпадает по стране с IPinfo, код принимает также его город и
   координаты, хотя второй источник город никак не подтвердил.
5. `adopt_tiebreak()` перезаписывает исходную запись. В кэше остаётся итоговое
   решение, но не исходный ответ ip-api. Это затрудняет разбор неверных решений.
6. `geo_confidence` обычно равен константе `medium`. Поле не является измеренной
   вероятностью правильности города. `validator_locations.js` и `map_popups.js`
   не объясняют пользователю источник и географическую неопределённость.
7. Ручные исключения уже существуют, но без обязательных доказательств,
   срока действия и области подтверждения. Факт ручной правки не доказывает
   точность до здания.

Сокращение TTL само по себе не исправит Sydney/Nyngan: свежий ответ ip-api
по-прежнему возвращает Nyngan.

100 км — настраиваемый порог очереди проверки, не радиус точности и не основание
автоматически переносить ноду. Расстояния рассчитаны по координатам, не по именам
городов. В 38 случаях ошибка может быть у любой базы или у обеих.
Числа **не являются оценкой процента ошибок сайта**: нет полной выборки с
независимо известным физическим расположением.

контрольный адрес. Сводка относится ко всем 416 IP. Файл содержит метаданные
версии базы и SHA-256 входных файлов; полные исходные snapshots и MMDB оставлены
локально в `/tmp/validatorclock-geo-audit/`.

## Насколько помогают бесплатные источники

| Источник | Практическое применение | Ограничение |
|---|---|---|
| DB-IP City Lite, локальный MMDB | Уже проверен: обнаруживает межгородские расхождения без запросов на каждый IP | Сам ошибается; Nyngan не исправляет; обновляется ежемесячно |
| MaxMind GeoLite City, локальный MMDB | Следующий кандидат для того же offline-сравнения; имеет поле accuracy radius | Бесплатные аккаунт и ключ обязательны; в этом аудите база не получена и её превосходство не установлено |
| IPinfo Lite | Проверка страны и ASN | Город отсутствует; платные планы не рассматриваются |
| ipwho.is Free | Дополнительная проверка города для ограниченного числа кандидатов | По текущим условиям 1000 запросов/день; нужен общий бюджет и Retry-After; не независимая физическая проверка |
| Geofeed оператора | Заявленная оператором привязка конкретного префикса | Неполное покрытие, возможны устаревшие или неточные записи |
| Looking Glass / существующие RIPE Atlas measurements | Проверка короткого списка спорных адресов сетевыми измерениями | ICMP может не отвечать; нет гарантированного покрытия; Atlas и его кредиты не проверены в этом эксперименте |

Условия источников проверены 10 сентября 2026:
[DB-IP](https://db-ip.com/db/download/ip-to-city-lite) — CC BY 4.0, требуется
атрибуция и ссылка на страницах, использующих данные;
[MaxMind](https://dev.maxmind.com/geoip/geolite2-free-geolocation-data/) —
бесплатная регистрация и лицензионный ключ;
[ipwho.is](https://ipwhois.io/documentation) — бесплатный endpoint без ключа.
Платные подписки, пробные платные планы и массовый сбор HTML-страниц IPinfo
в предлагаемую архитектуру не входят.

### Проверка geofeed на этой выборке

- [Hetzner](https://www.hetzner.com/geofeed.csv): покрывает **48 из 48** текущих
  IP AS24940. Названия городов согласуются с production. Для приведённого
  Falkenstein есть точное совпадение `178.63.165.64/26,DE,DE-SN,Falkenstein`.
- [Latitude.sh](https://geofeed.latitude.sh/): покрывает **1 из 12** текущих IP
  AS396356 (`45.250.254.61`, Ashburn). Исходный `67.213.125.125` и
  `64.34.88.165` не покрыты.
- [Prefix Broker](https://www.prefixbroker.com/prefixbroker-geofeed.csv): ссылка
  присутствует в RDAP Twinstake, но в полученном файле нет совпадения для
  `155.2.223.16`; на всей выборке покрытие равно нулю.

Итого эти три файла покрывают 49/416 IP. Это оценка только проверенных файлов,
не всего мирового покрытия geofeed. Совпадения и SHA-256 сохранены в
[geofeed-coverage.json](geofeed-coverage.json).

Файл Latitude.sh фактически отдаётся как HTML с `<p>`/`<br />`; при ручном
аудите удалены эти теги. Некоторые строки помещают `New South Wales` в поле
города. Нельзя без проверки геокодировать это как точный город. Универсальный
production-парсер должен придерживаться CSV по стандарту, а исключение для
известного формата оператора быть явным. Geofeed не содержит координат:
для карты понадобится однозначное сопоставление страна + регион + город,
например с локальным справочником GeoNames, и статус «центр города».

## Предлагаемые изменения

**Первый этап — наблюдение без автоматического переноса.** Оставить текущую
базовую геолокацию; подключить DB-IP City Lite локально как второе городское
мнение. В фоне сравнивать координаты, а не только строки названий. Записывать
отдельные признаки `country_disagreement` и `coordinate_disagreement`, список
кандидатов и метрики покрытия. Проверять все уникальные IP, включая адреса без
конфликта стран. Не скрывать ноду с карты только из-за нового городского
расхождения: показывать, что место приблизительное или спорное.

**Второй этап — отделить ответы источников от решения.** Хранить исходные
наблюдения `{source, fetched_at, country, region, city, coordinates, radius}`
отдельно от выбранного местоположения. Для решения хранить причины, использованные
источники и точность уровня страна/регион/город. Согласие по стране не повышает
уверенность в городе. Сохранить старые данные при сбое обновления, явно помечая
их возраст; не принимать просроченный tiebreak как свежее подтверждение.
Сейчас freshness проверяется при составлении очереди запросов, но не при
последующем использовании сохранённого tiebreak после неудачного обновления.

**Третий этап — подтверждение исключений.** Добавлять доверенные geofeed
по конкретным операторам/префиксам, с longest-prefix match, источником и датой.
Следовать [RFC 9632](https://www.rfc-editor.org/rfc/rfc9632.html): источник должен
быть связан с владельцем диапазона, а не просто найден где-то в интернете.
Перед production-интеграцией нужны ограничение размера/времени скачивания,
проверка диапазонов и защита загрузчика от произвольных внутренних URL.
Не назначать всему ASN один город и не считать наличие у провайдера площадки
достаточным доказательством местоположения конкретного IP.

Для оставшегося короткого списка — выборочные замеры из известных точек.
Хранить цель, расположение точки измерения, дату, число ответов, минимальную RTT
и исходный результат. Измерение соседа по /24 — косвенное; измерение нужного IP
предпочтительнее. Не превращать RTT в «точные координаты» и не создавать
постоянный массовый мониторинг на чужом публичном Looking Glass.

**Четвёртый этап — проверяемые исправления.** Расширить ручные исключения:
`evidence_urls`, `observed_at`, `expires_at`, `scope`, причина выбора. Два
измеренных примера подходят для обоснованных городских исключений после
реализации хранения доказательств. Для исправления координат указывать центр
города, без притворной точности дата-центра. При смене ASN/префикса или истечении
срока — повторная проверка. В tooltip показывать «приблизительно», а для
спорных точек — альтернативу; название базы можно оставить в подробностях.

Перед включением автоматических исправлений нужна контрольная выборка,
проверенная операторскими данными/замерами, и сравнение доли ошибочных переносов.
Текущие 38 расхождений — очередь исследования, не 38 готовых исправлений.
MaxMind следует прогнать через тот же аудит после получения бесплатного ключа;
обещать, что он исправит Sydney или улучшит весь набор, пока нельзя.

## Воспроизведение offline-аудита

Скрипт не ходит в сеть и не меняет входные файлы. Скачайте официальный MMDB
DB-IP City Lite, распакуйте `.gz`, установите `maxminddb` в отдельный venv.
В этом эксперименте использован `maxminddb==3.1.1`;
формат результата не зависит от сетевых API.

```sh
python3 -m venv /tmp/validatorclock-geo-audit/venv
/tmp/validatorclock-geo-audit/venv/bin/pip install maxminddb==3.1.1
/tmp/validatorclock-geo-audit/venv/bin/python scripts/audit_node_geolocation.py \
  --cache /tmp/validatorclock-geo-audit/geo_cache.json \
  --nodes /tmp/validatorclock-geo-audit/ton_map/ton_nodes.json \
  --nodes /tmp/validatorclock-geo-audit/everscale_map/everscale_nodes.json \
  --nodes /tmp/validatorclock-geo-audit/tycho_map/tycho_nodes_native.json \
  --mmdb /tmp/validatorclock-geo-audit/dbip-city-lite.mmdb \
  --output /tmp/validatorclock-geo-audit/audit.json
python3 -B -m unittest discover -s tests -p test_geolocation_audit.py
```

Скрипт также читает совместимые City MMDB, включая GeoLite City. Он учитывает
несколько нод/сетей на одном IP, не превращает отсутствие координат в расстояние
ноль и отмечает несовпадающие snapshots. Шесть regression-тестов проходят.
Rust/frontend не изменены, поэтому их тесты для этого аудита не запускались.
