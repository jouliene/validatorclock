## Охват и метод

Свежий снимок: **2026-09-10 02:42:52 UTC**. Из конфигурации production получен
полный список включённых сетей: TON, Everscale, Tycho testnet. Скопированы только
данные нод, опубликованные карты и geo cache. Входы фиксированы SHA-256 в [summary.json](summary.json).

Всего 498 валидаторов, 497 строк карты, **416 разных IP**. Сумма IP по сетям — 419:
три адреса используются более чем в одной сети. Исследование IP общее, результаты
показаны в каждой соответствующей сети. У одного валидатора Everscale IP отсутствует:
геолокация не может восстановить его. Две TON-записи — remembered IP резолвера;
они включены, поскольку присутствуют на карте. Ручной Roubaix сохранён.

Прогон использует **настоящий `Engine::refresh`**, порциями до 100 IP, с копией
production cache и реальным временем HTTP/измерений. Последние пригодные исходные
ответы сохраняются: 323 IP использовали недавний primary cache, 92 получили новый
основной ответ; ещё один — ручная локация. Обновлять без необходимости все 416 IP
внешними запросами не требовалось.

Общие DB-IP MMDB и geofeed Hetzner/Latitude взяты из уже скачанных официальных
файлов предыдущего аудита. Их скачивание не входит в стоимость этого запуска.
Каталог Globalping получен заново по сети. Нет платных сервисов или ключей.

Чтобы завершить очередь в одном исследовании, harness 53 раза сокращал **только
локальный срок следующей попытки IP**. Он не менял ограничения источников,
возраст наблюдений, сохранённые ID или результаты измерений. Ошибки ограничены
одной дополнительной попыткой на источник/IP в этом ускоренном обходе. Это проверка
результатов полного исследования, **не** доказательство реального времени обработки
нового сета production-планировщиком и **не** двухсуточное наблюдение.

Все 36 назначенных заданий завершились, все результаты получены. Сетевой проход
занял около 224 секунд после запуска теста; полный снимок результатов сохранён
в 02:50:20 UTC. Нет оставшихся незавершённых заданий Globalping. Спорные IP остаются
спорными после доступных проверок, а не пропущены ради завершения отчёта.

## Что изменилось на карте

Уникальные IP: 383 завершённых исследования + 32 спорных + 1 ручной.
Статусы: 331 `approximate`, 48 `operator_city`, 4 `measured_metro`, 32 `disputed`.
`approximate` означает отсутствие обнаруженного текущими проверками конфликта,
а не доказанную правильность города.

Каждое принятое измерение требует не менее трёх ответов точного IP в каждой из
двух разных сетей проб и коротких RTT в согласованной метрополии. Порог — эвристика,
метаданные проб могут ошибаться. Даже эти результаты не доказывают здание дата-центра.

Ещё **10 IP** `155.2.223.0/24` меняются с George Town, **Cayman Islands (KY)**
на Amsterdam, Netherlands (NL): `.16, .19, .23, .25, .26, .28, .31, .41, .42, .43`.
Здесь KY — код страны Каймановы острова, не американского штата Kentucky.
Физического подтверждения этих десяти переносов нет. Семь помечены `disputed`.

**Обнаруженный недостаток:** `.16`, `.28`, `.43` получают `approximate` без измерений.
Старые решения ipwho.is были возрастом примерно 50,6 / 50,6 / 123,5 часа. Они не
попали в новый набор свидетельств из-за двухсуточного срока миграции. ip-api и DB-IP
согласились на Amsterdam, конфликт не возник и Globalping не был вызван. Истечение
свежести данных не должно само по себе стирать историю крупного изменения локации.

Перед main нужно сохранять прошлую точку как историческое свидетельство и назначать
проверку крупного переноса/смены страны даже при согласии текущих баз. Это выявленная
доработка, **не исправление, уже внесённое в исследованный код**. Также остаётся
выбор компромисса для Sydney: дополнительное измерение может помочь, но снижать
порог только ради этого примера нельзя.

## Сравнение со старым алгоритмом на одинаковых основных ответах

Дополнительно запущен **реальный `legacy_refresh`**, но через локальные HTTP-ответы,
записанные новым прогоном. Primary TTL намеренно обойдён, чтобы оба алгоритма
получили одинаковые ip-api данные. Исходные cached IPinfo/tiebreak и их даты сохранены;
новых IPinfo-ответов этот replay не получает. Недостающий третий ответ считается
неудачным, а не придумывается. Внешних запросов — ноль.

Результат: **те же 11 отличий >100 км** — LA и десять адресов Cayman→Amsterdam.
Это подтверждает влияние логики выбора на эти точки, но не доказывает её правоту.
Такой replay не заменяет свежий независимый опрос всех старых источников.
Полные результаты: [legacy-replay.json](legacy-replay.json).

## Нагрузка

| Источник/операция | HTTP-запросы |
|---|---:|
| ip-api, пакетные запросы | 5 |
| ipwho.is | 28 |
| Globalping: создание заданий | 36 |
| Globalping: каталог + получение результатов | 37 |
| **Всего** | **106** |

Globalping вернул результаты **108 проб** для 36 IP **девяти ASN**:
AS16276, AS18450, AS203493, AS214434, AS24940, AS34959, AS396356, AS51167, AS57128.
Это общий алгоритм, не адаптер только для Latitude.

Повтор сразу после первого прохода: **0 HTTP**. Повтор после открытия журнала:
**0 HTTP**. После полного сбора измерений два повторных открытия/проверки всего набора
в 02:52:49 UTC: **0 и 0 HTTP**. Эти проверки выполнялись с реальным временем, не
с подменой на «через пять минут». Они подтверждают переиспользование результатов,
но не заменяют длительное наблюдение. Двухсуточный TTL и повторы ошибок отдельно
проверяются обычными интеграционными тестами; реальных 48 часов здесь не прошло.

106 — стоимость этого исследования с тёплым primary cache и готовыми общими файлами,
а не холодной установки и не прогноз трафика за месяц. Первичный main за это же
короткое время мог использовать недельный кэш почти без запросов; сравнивать
106 с нулём как показатель «хуже/лучше нагрузка» некорректно. Новый код исследует больше.

Повтор основного trial переиспользует журнал и потому не обязан воспроизводить
первоначальное число HTTP. Отчёт фиксирует именно выполненный запуск, а не обещание
детерминированного внешнего сервиса. Два локальных replay/verification не создают
новых измерений в успешном прогоне.
