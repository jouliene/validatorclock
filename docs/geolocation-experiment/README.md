# Экспериментальный резолвер: реализация и сравнение

Ветка: `experiment/node-geolocation-audit`. Базовая версия до изменений:
`6eb731a` (аудит без runtime-изменений), прежний runtime — `592a6f2`.
Main и production не переключались.

Реализован работающий Rust-резолвер, включённый по умолчанию в этой ветке.
Он автоматически исправил два независимо проверенных городских промаха и
существенно сократил повторные запросы в тестах. Превосходство точности на всей
выборке пока **не доказано**: для большинства серверов нет физической ground truth.
Не следует автоматически переносить этот эксперимент в main по числу изменённых точек.

## Новая схема работы

`src/node_locations/research/`:

- `mod.rs`: очередь IP, миграция старого кэша, обращения к источникам и постоянный журнал.
- `model.rs`: отдельные наблюдения и решение, сроки повторного использования, backoff, квоты.
- `sources.rs`: загрузка/проверка DB-IP MMDB, бесплатные HTTP-ответы и два проверенных geofeed.
- `operators.rs`: ограниченный адаптер Latitude.sh Looking Glass, проверка ответов ping.
- `tests.rs`: тесты реального асинхронного движка, сравнение старого/нового кода и opt-in trial.

Пятиминутный цикл читает локальные результаты DHT-резолвера. Разность IP работает
как очередь после green→blue / blue→green, а также подхватывает адреса, найденные
позже. Смена цвета сама по себе не инвалидирует геолокацию известного IP. Один IP
исследуется один раз независимо от количества валидаторов и сетей, использующих его.
Это не переделка DHT-резолвера: его опрос сети и получение IP остаются прежними.

Успешное исследование сохраняется на **90 дней**, включая результаты с приблизительной
геолокацией без обнаруженных противоречий. «Успешно» означает завершение доступных
проверок, а не математическое доказательство физического города. TTL настраивается.
Адреса могут перераспределяться; редкое обновление — осознанный компромисс.

Неудачные/отложенные исследования: 1 час → 6 часов → сутки → 3 дня → неделя.
Полностью исследованный, но не разрешённый конфликт повторяется раз в неделю.
При этом успешно полученные ответы сохраняются; при обычном повторе ошибки они
не запрашиваются заново. Для затянувшегося конфликта основные API-ответы обновляются
раз в неделю. Пока спор не разрешён, точка остаётся доступной с отметкой `disputed`.
При сбое обновления старой точки используется `stale`, а не пустая карта.

Журнал `<geo_cache>.research.json` сохраняет наблюдения, решение, причины,
следующую попытку, квоты и измерения. Каталог `<geo_cache>.research-data/` содержит
MMDB и geofeed. Квота записывается **до** HTTP-вызова; сбои тоже расходуют лимит.
Повреждение журнала не запускает исследование всех адресов с нуля.
Неактивные записи журнала хранятся до года; известные активные IP не удаляются.

## Бесплатные источники и ограничения нагрузки

| Источник | Когда запрашивается |
|---|---|
| ip-api batch | Для IP без пригодного исходного ответа; до 100 IP в одном запросе |
| DB-IP City Lite | Автоматическая загрузка общего MMDB; не более одной успешной загрузки выпуска в месяц и только при наличии работы |
| Hetzner / Latitude geofeed | Только когда исследуются их IP; успешный файл переиспользуется 30 дней |
| ipwho.is Free | Для конфликтов или отсутствующего основного ответа; успешный ответ сохраняется |
| Latitude Looking Glass | Только IP оператора с конфликтом или привязкой далеко от известных площадок; максимум две точки измерения на исследование |

По умолчанию: **128 HTTP-запросов в сутки на геолокацию нод суммарно по сетям**,
из них не более **6 запросов измерений**. Это потолок, а не расписание расходования.
Пакет со 100 IP считается одним HTTP-запросом. Соблюдаются `Retry-After`, `X-Rl`
и `X-Ttl`, а также локальная пауза источника. В базах посетителей и блокчейн-RPC
этот новый лимит ничего не меняет.

Ключи, регистрация, Python на сервере и платные планы не нужны. DB-IP загружается
самим Rust-процессом, gzip распаковывается с ограничением размера; новый файл
проверяется перед атомарной заменой. Рабочая база сохраняется при неудачном обновлении.
Сентябрьский MMDB занимает около 122 MiB; холодный запуск также требует его скачивания.
Неудачная загрузка общего файла не повторяется чаще раза в сутки.

Условия: [DB-IP City Lite](https://db-ip.com/db/download/ip-to-city-lite),
[ip-api batch](https://ip-api.com/docs/api:batch),
[ipwho.is](https://ipwhois.io/documentation).
DB-IP — CC BY 4.0, атрибуция добавлена в footer. Бесплатный ip-api предназначен
для некоммерческого использования. IPinfo Lite в новом пути не запрашивается;
его наличие и ключ не являются условием запуска новой геолокации.

## Как выбирается точка

Основной исходный ответ, локальная база и третий источник сохраняются отдельно.
Сравниваются страны и расстояния координат (>100 км), а не только имена городов.
Правило «два голоса против одного» удалено из нового пути. Пока нет более сильного
основания, выбирается основной ответ и явно сохраняется статус разногласия.
Это может менять старое решение большинства; такие переносы требуют проверки.

Geofeed проверяется по конкретному IP и наиболее узкому префиксу. Он подтверждает
название города, но не создаёт координаты здания. При несогласии возникает конфликт;
нет универсального переноса IP в «город провайдера». Для Latitude есть явный адаптер
его HTML-формата geofeed; регион `New South Wales` не принимается за город.

Адаптер измерений знает **метрополии оператора**, а не исследуемые IP. В runtime нет
исключений для `67.213.125.125` или `64.34.88.165`. Измерения назначаются на основании
ASN и расхождений данных. Для принятия города нужны не менее трёх ответов нужного
IP, несохранённый во внешнем кэше ответ Looking Glass и минимальная RTT ≤3 мс.
Не принимаются результат соседа по /24, просроченный результат или противоречивые
малые RTT из далёких городов. Сохраняются исходный вывод, цель, точка и время.

Порог 3 мс — эвристика приблизительной метрополии, **не** доказательство координат
или универсальная метрическая точность. Маркировка точки Looking Glass может быть
ошибочной; возможны anycast/прокси. У оператора могут появиться новые площадки, ещё
не включённые в адаптер. Большой ping никогда не используется как доказательство
другого города. Адаптер пока покрывает только Latitude, geofeed — Latitude и Hetzner.

## Сравнение на 416 IP production

Использована локальная копия опубликованных карт и geo cache из первого аудита.
Production checkout: `5cea791`; его геолокационный код совпадает с прежним локальным.
В snapshots 497 записей валидаторов, 416 уникальных IP. Один ручной override сохранён.

### Реальный запуск асинхронного движка

[live-comparison.json](live-comparison.json) — результаты для всех 416 IP,
[evidence.json](evidence.json) — исходные наблюдения и измерения изменённых точек.

| Результат | Значение |
|---|---:|
| HTTP-запросов при первом экспериментальном проходе | 12 |
| Из них ip-api batch / ipwho.is / Looking Glass | 1 / 9 / 2 |
| Повтор того же списка через 5 минут | 0 |
| Повтор после открытия движка из сохранённого журнала | 0 |
| Завершённые исследования / ожидающие продолжения | 378 / 37 |
| Ручное исключение | 1 |
| Точки, сместившиеся больше 100 км | 12 |
| Из них поддержанные прямыми измерениями | 2 |

Это **не стоимость установки с нуля**. В проходе были переиспользованы недавний
кэш production и ранее скачанные официальные файлы. Для одного прохода всей
выборки тест установил `max_ips_per_cycle=500`; обычное значение — 100 на сетевой
проход. На чистой установке добавятся пакетные запросы новых IP и загрузки файлов.
Дополнительные обращения выполнялись из локального окружения, не с production.

Девять вторичных ответов были получены по сети; десять имеющихся ответов ipwho.is
сохранены при миграции как свидетельства. Остальные исследования не теряются:
часть ожидает следующую попытку, часть — недельное обновление спорных данных.
Нулевые запросы на следующем пятиминутном цикле не означают, что спорные IP больше
никогда не будут проверяться.

| IP | Прежний результат | Новый результат | Основание |
|---|---|---|---|
| `67.213.125.125` | Nyngan | Sydney, `measured_metro` | Новый автоматический ping из Sydney: min **0,543 мс** |
| `64.34.88.165` | New York | Los Angeles, `measured_metro` | Новый автоматический ping из Los Angeles: min **2,097 мс** |
| 10 IP `155.2.223.0/24` | George Town, KY | Amsterdam, NL, `disputed` | Основной ответ и DB-IP — NL, сохранённый третий источник — KY; физическое подтверждение отсутствует |

Все десять переносов Twinstake остаются гипотезами, а не зачтёнными исправлениями.
Остальные спорные точки не были автоматически перенесены вслед за DB-IP.
В частности, не перенесён Hetzner `178.63.165.86` в другой Falkenstein.

Отдельно выполнен [offline replay](offline-comparison.json) теми же функциями
принятия решения, что использует runtime. Для него одним проходом получены свежие
ip-api-ответы для всех 416 IP (**5 пакетных запросов**, отдельно от 12 запросов live trial).
Replay дал те же сводные числа: 12 перемещений, 2 подтверждённых измерениями метрополии,
37 спорных точек. Даты данных и набор доступных источников зафиксированы; изменения
самих баз не объявляются заслугой алгоритма.

### Сравнение частоты запросов старого и нового кода

Старый код уже не запрашивал успешные IP каждые пять минут: TTL был семь дней.
Для неразрешённых IP у основного источника отрицательного кэша не было.

Следующие числа получены запуском **старого `legacy_refresh` и нового `Engine`**
с локальным HTTP-сервисом и управляемым временем. Внешние API в этих тестах не используются.

| Сценарий | Старый код | Новый код |
|---|---:|---:|
| Один успешный IP, 30 дней, включая первый запрос | 10 запросов: 5 ip-api + 5 IPinfo | 1 запрос ip-api |
| Один неразрешённый IP, сутки с циклом 5 минут | 288 | 6: три попытки по два источника |
| Известный IP снова появился после смены сета | Ответ из кэша, если не истекли 7 дней | Ответ из кэша до 90 дней |

В тесте успеха общий MMDB и операторские источники отключены: это сравнение
планировщика per-IP запросов, а не полная стоимость холодного запуска. Нельзя
наивно умножать эти числа на число нод: основной API пакетный, IP могут повторяться.
Дополнительный тест делает 8640 локальных циклов на одном сете, перезапуск,
появление нового IP и возврат старого: запрос выполняется только для нового адреса.

## Проверки и воспроизведение

- Все Rust-тесты: 362 прошли; четыре opt-in теста исключены из обычного запуска.
- Два новых opt-in прогона (offline replay и live trial) отдельно выполнены успешно.
- Frontend: 13 файлов тестов и синтаксические проверки прошли.
- `cargo clippy --offline --all-targets -- -D warnings`: без предупреждений.
- Тесты покрывают backoff, квоты после рестарта, Retry-After/X-Ttl, повреждённый
  журнал, обрыв HTTP-тела, возврат сета, истечение 90 дней, чужие/старые ping,
  конфликт малых RTT, geofeed IPv4/IPv6 и сохранение неопределённости в tooltip.

```sh
cargo test --offline
bash scripts/check-js.sh
# Требует локальных файлов из аудита; в сеть не ходит:
VALIDATORCLOCK_GEO_AUDIT_DIR=/tmp/validatorclock-geo-audit \
  cargo test --offline compare_saved_production_snapshot -- --ignored --nocapture
# Явный live trial: ограниченные внешние запросы; только локальная копия данных:
VALIDATORCLOCK_GEO_AUDIT_DIR=/tmp/validatorclock-geo-audit \
  cargo test --offline live_snapshot_trial -- --ignored --nocapture
```

Повтор live trial использует сохранённый журнал и потому может дать меньше запросов,
чем первый запуск; не удаляйте журнал ради обхода квот. Путь `/tmp/...` содержит
большие входные файлы и временное окружение; в git записаны отчёты, а не MMDB.
Настройки нового режима и сохранённого старого описаны в основном README.

## Решение о main

Улучшение по расписанию запросов подтверждено тестами и реальным повторным проходом.
По точности подтверждены два конкретных улучшения. Для остальных IP нет достаточной
ground truth, а десять изменений страны требуют отдельного подтверждения.
Поэтому оснований объявить глобально «значительно более точный резолвер» пока нет.
Перед переносом в main следует проверить эти десять IP и независимую выборку
других операторов; значительное улучшение точности нельзя измерять просто числом
переставленных точек или совпадением двух баз.
